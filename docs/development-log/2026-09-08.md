## 2. Pattern 재저장 시 중복 생성 문제 수정

### 작업 내용

서버에 이미 저장된 Pattern을 수정한 후 다시 저장하는 과정에서 새로운 Pattern이 생성되지 않고 기존 Pattern이 수정되도록 저장 로직을 점검했다.

### 문제

처음 저장한 Pattern을 수정한 뒤 다시 저장할 경우 기존 Pattern을 수정해야 하지만, 새로운 Pattern으로 저장될 가능성이 있었다.

하나의 Pattern을 계속 수정하는 경우에도 새로운 Pattern이 생성되면 서버에 동일한 Pattern이 여러 개 저장될 수 있었다.

### 원인

현재 Editor에서 서버에 저장된 Pattern의 ID를 `savedPatternId`로 관리하고 있었지만, 저장할 때 해당 ID의 존재 여부에 따라 생성 API와 수정 API를 구분하는 로직이 필요했다.

### 수정 내용

`ServerPatternPanel.tsx`

* `updatePattern as updatePatternApi` import 추가
* `savedPatternId`가 `null`인 경우 `createPatternApi()` 호출
* `savedPatternId`가 존재하는 경우 `updatePatternApi()` 호출
* 서버에서 반환된 Pattern ID를 `savedPatternId`에 저장
* 저장 후 Pattern 목록을 다시 불러오도록 처리
* 저장된 Pattern을 현재 선택된 Pattern으로 유지하도록 수정

저장 로직을 다음과 같이 구분했다.

```text
savedPatternId === null
    ↓
createPatternApi()
    ↓
POST /api/patterns/

savedPatternId !== null
    ↓
updatePatternApi()
    ↓
PATCH /api/patterns/{id}/
```

### 결과

처음 저장하는 Pattern은 새로운 Pattern으로 생성되고, 이미 저장된 Pattern은 기존 Pattern ID를 기준으로 수정되도록 변경했다.

따라서 하나의 Pattern을 수정한 후 다시 저장하더라도 새로운 Pattern이 중복 생성되지 않고 기존 Pattern이 업데이트되도록 개선했다.

### 테스트

```text
Pattern 생성
    ↓
첫 번째 저장
    ↓
새 Pattern 생성
    ↓
Pattern ID 저장
    ↓
Pattern 수정
    ↓
다시 저장
    ↓
기존 Pattern 수정
```

테스트 결과 첫 번째 저장에서는 새로운 Pattern이 정상적으로 생성되었으며, 이후 같은 Pattern을 수정하고 다시 저장했을 때 기존 Pattern이 수정되는 것을 확인했다.

기존 Pattern의 ID가 유지되고 새로운 Pattern이 중복 생성되지 않는 것을 확인했다.

## 3. 새로운 Pattern 생성 및 Image Import 시 Runtime Error 발생

### 작업 내용

로그아웃한 상태에서 새로운 Pattern을 생성하거나 Image Import를 수행하는 과정에서 Editor 화면이 흰색으로 변하는 문제를 확인했다.

### 문제

Browser Console에서 다음 오류가 발생했다.

```text
Uncaught TypeError:
Cannot read properties of undefined (reading 'hex')

at PatternEditor (PatternEditor.tsx:893:80)
```

오류가 발생한 부분은 `PatternEditor.tsx`의 StatusBar에 현재 선택된 색상의 `hex` 값을 전달하는 코드였다.

기존 코드는 다음과 같았다.

```tsx
selectedColorHex={
    pattern.palette[selectedColor].hex
}
```

새로운 Pattern이 적용된 이후 `selectedColor`가 새로운 Pattern의 Palette에 존재하지 않는 경우 `pattern.palette[selectedColor]`가 `undefined`가 될 수 있었다.

### 원인

기존 Pattern에서 선택되어 있던 색상 상태와 새로운 Pattern의 Palette가 서로 일치하지 않을 수 있기 때문이었다.

예를 들어 기존 Pattern에서 특정 색상을 선택한 상태에서 새로운 Pattern으로 교체되면 새로운 Pattern의 Palette에는 기존에 선택했던 색상이 없을 수 있다.

```text
기존 Pattern
Palette
 ├── White
 ├── Black
 └── Red

selectedColor
    ↓
Red
```

새로운 Pattern으로 교체한 이후:

```text
새로운 Pattern
Palette
 ├── White
 └── Black

selectedColor
    ↓
Red
```

기존 `selectedColor`는 새로운 Palette에 존재하지 않게 된다.

이 상태에서 다음 코드를 실행하면 존재하지 않는 Palette 데이터를 참조하게 된다.

```tsx
pattern.palette[selectedColor].hex
```

그 결과 `undefined`의 `hex`를 읽으면서 Runtime Error가 발생했다.

### 수정 내용

`usePattern.ts`

* 새로운 Pattern으로 전체 Pattern 데이터를 교체하기 위한 `replacePattern()` 함수 추가
* 새로운 Pattern의 Palette에 현재 `selectedColor`가 존재하는지 확인
* 기존 `selectedColor`가 존재하지 않는 경우 새로운 Palette의 첫 번째 색상을 선택
* `createPattern()`, `loadPattern()`, `clearPattern()`에서 Pattern을 교체할 때 `replacePattern()` 사용
* `replacePattern()`을 Hook에서 반환하여 `PatternEditor.tsx`에서도 사용할 수 있도록 수정

```tsx
/**
 * 새로운 Pattern으로 교체한다.
 *
 * Pattern이 변경될 때 현재 선택된 색상이
 * 새로운 Palette에도 존재하는지 확인한다.
 *
 * 만약 기존 selectedColor가 새로운 Palette에 없다면
 * Palette의 첫 번째 색상을 자동으로 선택한다.
 */
const replacePattern = (newPattern: PatternData) => {
    setPattern(newPattern);

    // 새로운 Pattern의 Palette에
    // 현재 선택된 색상이 존재하는지 확인한다.
    const colorExists = newPattern.palette.some(
        color => color.id === selectedColor
    );

    // 기존 선택 색상이 없다면
    // 새로운 Palette의 첫 번째 색상을 선택한다.
    if (!colorExists && newPattern.palette.length > 0) {
        setSelectedColor(newPattern.palette[0].id);
    }
};
```

`PatternEditor.tsx`

* Image Import 결과로 생성된 Pattern을 직접 `setPattern()`으로 적용하지 않고 `replacePattern()`을 사용하도록 수정

Image Import 흐름을 다음과 같이 변경했다.

```text
이미지 선택
    ↓
FastAPI
    ↓
PatternData 생성
    ↓
replacePattern()
    ↓
새로운 Pattern 적용
    ↓
Palette 확인
    ↓
selectedColor 동기화
```

### 결과

새로운 Pattern을 생성하거나 Image Import를 수행할 때 기존 `selectedColor`가 새로운 Palette에 존재하지 않는 경우 새로운 Palette의 첫 번째 색상이 자동으로 선택되도록 수정했다.

Pattern 데이터와 선택된 색상 상태가 서로 다른 Pattern을 참조하는 문제를 해결했다.

## 4. StatusBar Palette 접근 오류 방지

### 작업 내용

`replacePattern()`을 통해 `selectedColor`와 새로운 Palette를 동기화했지만, UI에서 예상하지 못한 상태가 발생하더라도 Editor가 Runtime Error로 종료되지 않도록 StatusBar의 Palette 접근에도 방어 로직을 추가했다.

### 수정 내용

`PatternEditor.tsx`

기존 StatusBar의 `selectedColorHex` 접근 방식을 다음과 같이 수정했다.

```tsx
selectedColorHex={
    pattern.palette[selectedColor]?.hex ??
    pattern.palette[0]?.hex ??

}
```

### 동작

```text

    ↓
해당 색상의 hex 사용

    ↓
Palette 첫 번째 색상 사용

Palette 자체가 비어 있음
    ↓
#000000 사용
```

### 결과

`selectedColor`에 해당하는 Palette 항목이 존재하지 않는 예상하지 못한 상태에서도 `undefined.hex` 오류가 발생하지 않도록 방어 로직을 추가했다.

이를 통해 Pattern 교체 과정에서 발생할 수 있는 추가적인 Runtime Error를 방지했다.

## 6. Image Import Panel 긴 파일명 UI 문제 수정

### 작업 내용

Image Import 기능을 테스트하는 과정에서 이미지 파일명이 매우 긴 경우 파일명 표시 영역의 크기 때문에 Import Panel의 너비가 증가하는 문제를 확인했다.

### 문제

긴 파일명을 가진 이미지를 선택하면 파일명 문자열의 길이에 따라 내부 영역의 너비가 커지면서 Panel 전체 Layout에 영향을 주었다.

### 원인

파일명 표시 영역에 긴 문자열을 제한하기 위한 너비와 줄바꿈 처리가 충분하지 않았다.

### 수정 내용

`ImportImagePanel.tsx`

파일명 표시 영역에 다음 스타일을 추가했다.

```tsx
width: "100%",
minWidth: 0,
display: "-webkit-box",
WebkitLineClamp: 2,
WebkitBoxOrient: "vertical",
overflow: "hidden",
overflowWrap: "anywhere"
```

각 속성을 사용하여 다음과 같이 처리했다.

* `width: "100%"`으로 파일명 영역을 Panel의 너비에 맞춤
* `minWidth: 0`으로 긴 파일명 때문에 Flex 영역이 강제로 늘어나지 않도록 처리
* `display: "-webkit-box"`로 여러 줄 표시
* `WebkitLineClamp: 2`로 최대 2줄까지 표시
* `WebkitBoxOrient: "vertical"`로 세로 방향 줄 제한 적용
* `overflow: "hidden"`으로 제한된 영역 밖의 문자열 숨김
* `overflowWrap: "anywhere"`로 긴 파일명도 영역 안에서 줄바꿈

### 결과

긴 파일명을 가진 이미지를 선택하더라도 Image Import Panel의 너비가 증가하지 않도록 수정했다.

파일명이 길 경우 Panel 내부에서 줄바꿈되며 최대 2줄까지 표시되도록 개선했다.

## 7. Public Pattern 기능의 현재 상태 확인

### 작업 내용

Pattern 저장 UI에 있는 `is_public` 옵션을 확인하고, Pattern을 Public으로 저장했을 때 다른 사용자가 해당 Pattern을 볼 수 있는지 현재 Django API 구조를 기준으로 확인했다.

### 현재 Pattern 데이터

```text
owner
title
width
height
is_public
pattern_data
created_at
updated_at
```

Pattern 모델에는 이미 `is_public` 필드가 존재한다.

### 현재 API 동작

현재 Pattern 목록과 상세 조회는 로그인한 사용자의 Pattern만 조회하도록 구현되어 있다.

```python
Pattern.objects.filter(owner=self.request.user)
```

따라서 `is_public=True`로 저장하더라도 현재 API 구조에서는 다른 사용자가 해당 Pattern을 조회할 수 없다.

현재 구조는 다음과 같다.

```text
사용자 A
    ↓
Pattern 저장
    ↓
is_public = True
    ↓
사용자 A의 Pattern 목록에 표시

사용자 B
    ↓
GET /api/patterns/
    ↓
사용자 B 자신의 Pattern만 조회
```

### 결과

`is_public` 필드는 Pattern의 공개 여부를 저장할 수 있지만, 현재는 다른 사용자가 Public Pattern을 조회할 수 있는 API와 Frontend 화면이 구현되어 있지 않다는 것을 확인했다.

Public Pattern 기능은 현재 구현된 기능이 아니라 향후 확장 기능으로 분류했다.

9. Private Pattern이 다른 사용자에게 노출되지 않는지 권한 테스트
10. Public / Private Pattern 전체 사용자 시나리오 테스트

기존 개인 Pattern API는 계속 로그인한 사용자의 Pattern만 조회할 수 있도록 유지한다.

---

## 10. 개발 메모

현재 Django와 기존 FastAPI는 동시에 유지한다.

```text
React
 │
 ├── FastAPI
 │    └── 이미지 → PatternData
 │
 └── Django
      ├── 인증
      └── Pattern 저장 / 관리
             │
             ▼
           MySQL
```

기존 Editor는 로그인하지 않아도 사용할 수 있도록 유지한다.

```text
Anonymous
    ↓
Editor 사용 가능
    ├── Pattern Editing
    ├── Image Import
    ├── Palette
    ├── PNG Export
    └── JSON Export

로그인 사용자
    ↓
기존 Editor 기능
    +
Server Pattern
    ├── Save
    ├── Load
    ├── Update
    └── Delete
```

기존 FastAPI 이미지 변환 기능은 유지하고, Django는 사용자 인증 및 Pattern 저장과 관리를 담당하는 Backend로 계속 확장한다.

`replacePattern()`은 Pattern 전체가 교체되는 상황에서 Pattern 데이터와 선택된 색상 상태가 서로 다른 Pattern을 참조하지 않도록 하기 위한 상태 관리 함수로 사용한다.

`ServerPatternPanel`의 `savedPatternId`는 현재 Editor에서 작업 중인 서버 Pattern을 식별하고, 최초 저장과 기존 Pattern 수정 요청을 구분하는 데 사용한다.
